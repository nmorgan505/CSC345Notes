01 · OS Overview

Learning Objectives

By the end of this lecture, you should be able to:

  • Explain what an OS does using the three-role framework (Referee, Illusionist, Glue)
  • Describe how multiprogramming improved CPU utilization over earlier batch systems
  • Place the memory hierarchy levels in order and explain the access/capacity tradeoff at each level
  • Define the process and virtual memory abstractions at a conceptual level

What Just Happened?

Double-click an app. The window appears. Simple.

Except it isn’t. In the fraction of a second between your click and that window, your operating system allocated memory, loaded executable code from disk, created a process, set up a virtual address space, wired up I/O channels, and handed off execution — all while continuing to run your music player, your browser, your clock, and everything else. None of that required any thought on your part.

This course is about understanding those thousand invisible things. Once you do, a lot of computing behavior that seemed arbitrary — why does your computer slow down with too many tabs open? why does your program crash with a segfault? why does adding more RAM help? — starts making sense.

Opening Discussion

Before moving forward: what do you think the OS is actually responsible for? What would break if it didn’t exist? Take a few guesses from the class before continuing.

What an Operating System Actually Is

An operating system sits between hardware and the applications running on top of it. The hardware provides raw computational power. Applications want to use that power. The OS is the intermediary that makes the negotiation safe, efficient, and transparent.

It plays three distinct roles simultaneously:

Referee. Multiple programs run at the same time, and they all want the same resources: CPU time, memory, disk access, network bandwidth. Left to themselves, programs would constantly step on each other. The OS arbitrates access and enforces isolation — your text editor cannot read Chrome’s memory, and Chrome cannot starve your music player of CPU time.

Illusionist. Every running program believes it has exclusive access to the CPU and to a large, contiguous block of memory. Neither is true. The OS creates this illusion through scheduling and virtual memory, covered in depth in later lectures. Programmers can write code as if they own the machine, while the OS quietly ensures dozens of programs share it.

Glue. Hardware is diverse and messy. Your program shouldn’t need to know whether it’s writing to an NVMe SSD or a spinning hard drive, or whether its display is an OLED or an LCD. The OS provides a consistent set of abstractions — files, sockets, processes — that work regardless of what hardware is underneath.

Class Activity: Name That Role

For each of the following OS behaviors, identify which role it serves — Referee, Illusionist, or Glue. Discuss briefly:

  1. Preventing Process A from reading Process B’s memory
  2. Making printf() work on both Linux and macOS without code changes
  3. Making a program think it has 8 GB of RAM on a machine with only 4 GB installed
  4. Stopping a runaway process from using 100% of the CPU indefinitely

(These can overlap — some behaviors serve more than one role.)

OS Services

The OS provides services that applications depend on: an environment for program development and execution, I/O access, controlled access to the filesystem, system-wide access control, error detection, and resource accounting. These aren’t glamorous, but remove any one and software development gets dramatically harder. A single write() call, for instance, involves the OS arbitrating disk access, managing a buffer cache, handling errors, updating filesystem metadata, and ensuring other processes don’t clobber the same file simultaneously — all hidden behind a one-line API.

A Brief History of How We Got Here

Understanding the history makes the OS’s design decisions less arbitrary.

Serial Processing (1945–1955). No OS. Programmers reserved machine time on a sign-up sheet, walked in, set up their program physically, ran it, and collected output. Setup inefficiency and scheduling waste were enormous.

Simple Batch Systems (1955–1965). A monitor automated the transition between jobs. Programs were batched on tape and run sequentially without operator intervention. Better utilization, but the CPU still sat idle waiting for I/O.

Multiprogramming (1965–1980). The key insight: when one job waits for I/O, run a different job. Keep several programs in memory at once. Consider the numbers: if reading a file takes 15µs, executing 100 instructions takes 1µs, and writing takes 15µs, a single job keeps the CPU busy only about 3% of the time. With multiple jobs overlapping their I/O, CPU utilization climbs dramatically.

Time-Sharing (1970s–present). Multiprogramming maximized batch throughput, but interactive users needed fast response time. Time-sharing gave each user a short CPU slice in rapid rotation, creating the illusion of a dedicated machine. This is how your OS still works today.

Key Calculation: Multiprogramming Utilization

If a process spends fraction p of its time waiting for I/O, and there are n processes in memory, the probability all are waiting simultaneously is pn. CPU utilization ≈ 1 − pn.

Example on the board: 80% I/O wait (p = 0.8):

Processes (n) CPU Utilization
1 20%
3 49%
5 67%
10 89%

This is why adding more RAM (allowing more processes) directly improves CPU utilization — up to a point.

Processes and Memory: A Preview

Two abstractions appear throughout this course. A process is a running program — not just the code, but the program’s data, stack, heap, and all the OS bookkeeping: what it’s waiting for, what resources it holds, where it is in execution. Every program you launch becomes a process.

Virtual memory gives each process the illusion of its own large, private address space. The OS maps the addresses the program sees to wherever data actually lives in physical RAM or on disk. This is how programs whose combined memory needs exceed physical RAM can all run simultaneously.

The Memory Hierarchy

There is a fundamental and unavoidable tradeoff between speed and capacity that shapes every OS decision about memory:

Level Example Speed Capacity
Registers CPU registers ~1 cycle Bytes
L1/L2/L3 Cache On-chip SRAM 4–40 cycles KB–MB
Main Memory DRAM ~100 cycles GB
Secondary Storage SSD / HDD Millions of cycles TB

The OS cannot change this hierarchy — it’s physics and economics. What it can do is manage movement between levels intelligently. The principle of locality makes this tractable: programs tend to access the same memory locations repeatedly in short time windows. Cache exploits this by keeping recently used data close to the CPU. Cache is entirely hardware-managed — the OS doesn’t control it — but understanding it is essential for writing efficient software and understanding system behavior.

Security, Fault Tolerance, and Scheduling

The OS handles security through the CIA triad: Confidentiality (only authorized users see data), Integrity (only authorized users modify data), and Availability (authorized users can access data reliably). It enforces all three through access control, process isolation, and virtual memory protection.

Fault tolerance keeps the system running when something breaks. Reliability R(t) is the probability of correct operation up to time t. Key metrics: Mean Time to Failure (MTTF) — how often things break — and Mean Time to Repair (MTTR) — how long to fix them. Availability = MTTF / (MTTF + MTTR). Redundancy through backup components, data replication, and checkpointing is how high-availability systems achieve good numbers on these metrics.

Scheduling and resource management decide how CPU time, memory, and I/O are allocated. Fairness, efficiency, and responsiveness are all in tension — the right tradeoff depends entirely on the workload. Lectures 4 and 5 are dedicated to this.

Multicore Considerations

Modern hardware has shifted dramatically toward many-core designs. Parallelism now exists at three levels: within a single instruction stream (handled by the CPU itself), across threads within a process, and across independent processes. The OS must assign work to many cores efficiently, synchronize shared data, and balance load — none of which is straightforward. This is one of the central engineering challenges in modern OS design.
