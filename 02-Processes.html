02 · Processes

Learning Objectives

By the end of this lecture, you should be able to:

  • Describe the four memory regions that make up a process
  • Explain what information the PCB contains and why each field is necessary
  • Trace a process through its five lifecycle states and explain what triggers each transition
  • Walk through the steps of a context switch and explain why it has a performance cost
  • Explain what fork() does and the fork-exec pattern

Open Your Task Manager

Press Ctrl+Shift+Esc on Windows, or run ps aux in a Linux terminal. What you see is a list of processes — every program the OS is currently tracking. There are probably 100–200 of them, even on a quiet system. For each one, the OS knows its ID, CPU usage, memory consumption, state, and dozens of other details.

The data structure that holds all of that information for a single process is called the Process Control Block (PCB), and it is the most important data structure in the OS. This lecture is about what’s in it, why, and how the OS uses it to manage dozens of running programs simultaneously.

What a Process Is

A process is a program in execution. The distinction matters: a program is passive — an executable file sitting on disk. A process is active — that program loaded into memory, running or waiting to run, with its own dedicated state and resources.

Every process occupies four distinct regions in memory:

  • Text section — the executable instructions themselves
  • Data section — global variables and static data
  • Heap — dynamically allocated memory (malloc, new), grows and shrinks at runtime
  • Stack — local variables, function parameters, return addresses; a LIFO structure that grows with each function call and shrinks as they return

At any moment, the OS also tracks the process’s PID, current state, priority, program counter value, and the contents of all CPU registers. This execution context is what makes it possible to pause a process mid-execution, run something else, and resume later without the process knowing it was ever interrupted.

Quick Check

Draw a diagram of a process’s memory layout — text, data, heap, stack — and label which direction the heap and stack grow. Which two can collide if a program uses too much memory? This is a common interview question and a real system failure mode.

The Process Control Block

The PCB is the OS’s per-process record. It’s a single data structure containing everything the OS needs to manage that process:

Process Identification — the numeric PID, the parent’s PID (PPID), and the user ID of the process owner.

Process State — one of five values: New, Ready, Running, Blocked/Waiting, or Terminated (described in the next section).

CPU Context — the values of all registers at the moment the process was last paused. When the process resumes, these get loaded back into the CPU. Without this, there would be no way to resume a process — the CPU state would be permanently lost.

Memory Information — where this process’s pages or segments live in physical memory, and the base/limit registers defining its valid address space.

Scheduling Information — the process’s priority, time spent waiting, time of last execution, and whatever other data the scheduling algorithm requires.

I/O Status — which files are open, which devices are in use, and any pending I/O requests.

The PCB’s Achilles Heel

Every running process is described by a PCB, and all PCBs are managed by the same kernel code. A bug in OS process management could corrupt every PCB simultaneously — crashing every process at once. This is why PCB-touching kernel code is among the most carefully written and tested code in existence. It is a genuine single point of failure for the entire system.

Process States and Transitions

A process is always in exactly one of five states:

  • New — being created; the OS is allocating memory and initializing the PCB
  • Ready — in memory and ready to run, waiting for the scheduler
  • Running — instructions executing on a CPU core right now
  • Blocked (Waiting) — waiting for an external event (I/O, a signal, a lock); cannot proceed even if a CPU is available
  • Terminated — execution finished; OS is cleaning up
Board Exercise: Trace These Transitions

Work through the following scenario as a class and draw the state transitions:

  1. The OS creates a new process for an app the user just launched
  2. The scheduler selects it for execution
  3. The process calls read() to load a file from disk
  4. The disk I/O completes
  5. The scheduler selects the process again
  6. The process calls exit()

Which transition is most expensive? Which one is under the process’s control vs. the OS’s control?

Suspended processes add an extra layer. When memory is scarce, the OS can swap a blocked process out to disk entirely, freeing its RAM for others. The swapped process enters a Suspended state — not in memory, cannot run until swapped back in. Modern SSDs make this far less painful than it was in the spinning-disk era.

The Context Switch

The context switch is how the CPU moves between processes. When the OS decides to switch from Process A to Process B:

  1. Save A’s entire CPU state (all registers, program counter, flags) into A’s PCB
  2. Update A’s state from Running to Ready or Blocked
  3. Select Process B from the ready queue; update B’s state to Running
  4. Load B’s CPU state from its PCB into the actual CPU registers
  5. Jump to where B’s program counter points

From B’s perspective, it was never interrupted. The switch is invisible to both processes.

Context switches aren’t free. The save/restore takes time, and because B has different memory access patterns than A, much of the CPU cache is now stale — the first memory accesses will be slow cache misses. This is one reason modern OSes try to minimize unnecessary switches, and why thread switching (next lecture) is cheaper than full process switching.

Process Creation: fork()

On Unix/Linux, every process is created via fork(). When a process calls fork(), the OS:

  1. Allocates a new PCB and assigns a unique PID to the child
  2. Gives the child a copy of the parent’s address space
  3. Increments reference counts on all open files (both parent and child now own handles)
  4. Places the child in Ready
  5. Returns the child’s PID to the parent, and 0 to the child

Parent and child then run independently. The child typically calls exec() immediately, replacing its inherited copy of the parent’s program with a new executable. This fork-exec pattern underlies every program launch on Unix — your shell forks itself, then the child execs the program you typed.

Class Activity: Read This Code 
pid_t pid = fork();
if (pid == 0) {
    printf("I am the child, PID = %d\n", getpid());
} else {
    printf("I am the parent, my child's PID = %d\n", pid);
}
printf("This line runs in both processes\n");

How many times does the last printf execute? What does the output look like? Can you predict the exact ordering? Why or why not?

Processes terminate voluntarily (exit()) or involuntarily (fatal error, kill signal). On termination, resources are freed and the PCB is removed — but only after the parent calls wait() to collect the exit status. Until then, the terminated process is a zombie: no resources, PCB preserved, waiting for the parent to acknowledge it.

Interrupts, Traps, and the Kernel

Three mechanisms let the CPU stop what it’s doing and handle something else:

Interrupts — asynchronous signals from hardware: a disk read completing, a timer firing, a network packet arriving. The CPU saves state and jumps to a kernel handler.

Traps — synchronous events from the current instruction: division by zero, segfault (invalid memory access), illegal instruction. The OS handles it, usually terminating the offending process.

System calls — explicit requests from a process to the kernel: open a file, allocate memory, fork a child. The process switches from user mode to kernel mode, the kernel does the work, and returns.

The kernel manages all of this — process creation and scheduling, memory management, I/O, and interrupt handling — running in privileged kernel mode with access to instructions user processes can never execute.

Live Demo

Run strace ls in a terminal (Linux/WSL). strace intercepts and prints every system call a process makes. You’ll see openat(), read(), write(), close(), and more — every interaction between ls and the kernel, completely exposed. Try it on other simple commands: strace echo hello, strace pwd. What’s the most surprising call you see?

Discussion Prompt

fork() creates a child with a copy of the parent’s address space. For a process using 2 GB of RAM, creating that copy sounds catastrophically slow. But fork() is actually fast. How? What optimization do modern OSes use to avoid eagerly copying all that memory? (This is worth working through carefully — the answer has implications for understanding both performance and the copy-on-write technique used throughout the kernel.)
