03 · Threads

Learning Objectives

By the end of this lecture, you should be able to:

  • Explain the difference between a process and a thread and what each one owns
  • Compare the advantages and disadvantages of User-Level Threads vs. Kernel-Level Threads
  • Describe the three thread states and the four operations that change them
  • Write and reason about basic pthreads code
  • Explain why race conditions occur and what fork-join parallelism looks like

Why Can You Scroll While the Page Is Loading?

Open a browser and navigate to a heavy website. While images and scripts are still downloading, you can scroll, click, type in the address bar, and switch tabs. How?

The browser isn’t taking turns between downloading and responding to you — it’s doing multiple things genuinely at once, within the same program. One part handles network I/O, another renders what’s already arrived, another listens for your input. These are threads: independent flows of execution sharing the same process.

That’s the thread model in a sentence: shared memory, independent execution. Understanding it changes how you think about performance, about writing concurrent programs, and about why some bugs are so hard to reproduce.

Processes vs. Threads

Recall from last lecture that a process has two responsibilities: owning resources and executing instructions. Threads split these apart.

A process is the unit of resource ownership. It has a virtual address space, open files, I/O channels, and all the OS bookkeeping that goes with them.

A thread is the unit of execution within a process. It has its own program counter, register set, and stack — the minimum needed to independently track where it is in execution. But it shares the process’s code, data, and file handles with every other thread in the same process.

Board Exercise: What’s Shared, What’s Private?

Draw a process containing three threads. Label which resources are shared across all three threads and which are private to each thread.

Shared: code, data, heap, open files

Private to each thread: program counter, registers, stack

Follow-up: if Thread 1 writes to a global variable, which threads see the change immediately?

This distinction has practical consequences. Creating a new thread is much cheaper than a new process — no new address space, no new file descriptor table, no full PCB copy. Switching between threads in the same process is cheaper — the memory mappings don’t change, so the cache stays warm. And threads can communicate simply by reading and writing shared memory, without pipes, sockets, or any IPC overhead.

The cost is coordination. Because threads share memory, any thread can corrupt any shared data. Without careful synchronization — the subject of Lecture 6 — this produces silent, timing-dependent bugs. Threads make some things simple and other things genuinely hard.

Thread States and Operations

Thread state mirrors process state, simplified to three values: Running, Ready, and Blocked. The key difference from processes: a blocked thread does not block the other threads in its process. If the download thread blocks on a slow network connection, the render thread and input thread continue running. This is precisely what makes browsers responsive.

Four operations drive state changes: Spawn creates a new thread, Block suspends a thread waiting for an event, Unblock moves a blocked thread back to Ready, and Finish terminates the thread.

Two exceptions: suspending a process suspends all its threads — there’s no way to keep some threads running while the process is swapped out. Terminating a process terminates all threads within it. The process is the container; removing the container removes everything inside.

User-Level vs. Kernel-Level Threads

The OS doesn’t have to know threads exist. Thread management can happen entirely in user space, invisible to the kernel. Alternatively, the kernel can manage threads directly. Both approaches exist and both have real tradeoffs.

User-Level Threads (ULTs) are managed by a user-space library. The kernel sees only a single-threaded process. Thread operations — creation, switching, scheduling — happen without kernel involvement, making them fast and portable across different OSes.

The problem: when a ULT makes a blocking system call (like reading a file), the kernel blocks the entire process, not just that one thread. All other ULTs freeze. The kernel doesn’t know they exist. This cripples I/O concurrency. The workaround is jacketing — converting blocking calls to non-blocking ones and polling — which is complex and unpleasant to do correctly.

The second problem: on a multiprocessor, only one ULT runs at a time. The kernel allocates exactly one CPU to the process. True parallelism is impossible.

Kernel-Level Threads (KLTs) are managed by the kernel. Each thread is a real scheduling entity. One thread blocking on I/O doesn’t affect the others. Multiple threads can run simultaneously on multiple cores. Windows uses this model.

The cost: every thread operation — creation, context switch, blocking — requires a system call and a mode switch into kernel mode. With many frequently-switching threads, this overhead accumulates.

The combined approach does creation and scheduling in user space (fast) but uses the kernel for CPU assignment (parallel). This is essentially how modern runtimes work — Go’s goroutines, Java virtual threads, Python’s asyncio — many lightweight user-space units multiplexed onto a smaller pool of kernel threads.

The pthreads API

On Unix/Linux, the standard thread API is POSIX threads (pthreads), a user-space library interfacing with kernel threads underneath.

// Create a thread running function func with argument arg
int pthread_create(pthread_t *tid, pthread_attr_t *attr,
                   void *(*func)(void *), void *arg);
// Returns 0 on success, nonzero on error

// Wait for a thread to finish; collect its return value
int pthread_join(pthread_t tid, void **return_value);

// Terminate the calling thread
void pthread_exit(void *return_value);

// Voluntarily yield the CPU to another thread
pthread_yield();

pthread_create takes a function pointer — the function the new thread runs — and an argument to pass it. The thread runs until the function returns or it calls pthread_exit. The parent uses pthread_join to wait for the child, exactly as a process uses wait() for a child process.

Class Activity: A Broken Counter

The following program has a race condition. Compile it, run it several times, and observe the output:

#include <stdio.h>
#include <pthread.h>

int counter = 0;

void *increment(void *arg) {
    for (int i = 0; i < 1000000; i++)
        counter++;
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
    printf("counter = %d\n", counter);
}
// Compile: gcc -pthread broken_counter.c -o broken_counter

Expected result: 2,000,000. Actual result: varies. Why? (Hint: counter++ is not one instruction.) We’ll fix this properly in Lecture 6.

Multicore Programming

Having multiple cores available doesn’t make programs faster automatically. Concurrent execution means tasks make progress interleaved over time — possible even on a single core through rapid switching. Parallel execution means tasks run at literally the same instant on different cores — requires multiple cores. Parallelism implies concurrency; concurrency does not imply parallelism.

Using threads well on multicore hardware requires thinking carefully about: how to divide work, how to balance load across cores, how threads share data, which computations depend on others’ results, and how to test and debug behavior that varies with timing.

Fork-Join Parallelism

Fork-join is the cleanest pattern for expressing parallel work: break a problem into subproblems, fork a thread for each, and join when all are done.

if problem is small enough:
    solve the problem directly

else: (problem is large or can be broken down)
    subtask1 = fork(new Task(subset of problem))
    subtask2 = fork(new Task(subset of problem))

    result1 = join(subtask1)
    result2 = join(subtask2)

    return result1 combined with result2

Merge sort, parallel reduce, map-reduce — all are fork-join at heart. Fork creates parallel execution; join synchronizes results. Java’s ForkJoinPool, Go’s goroutines with channels, and Rust’s Rayon library all implement variations of this.

Threading Gotchas

When fork() is called from a multithreaded process, Linux creates a child with only a single thread — the one that called fork(). The other parent threads don’t exist in the child. This is a subtle trap: if the parent’s threads held any locks at the moment of the fork, the child process inherits those locks in a locked state that can never be unlocked. Programs that mix fork() and threads must handle this carefully.

exec() in a multithreaded context replaces the entire process — all threads — with the new program, which starts fresh with a single thread. No surprises there.
