04 · Multiprocessor Scheduling

Learning Objectives

By the end of this lecture, you should be able to:

  • Distinguish loosely coupled, functionally specialized, and tightly coupled (SMP) multiprocessor systems
  • Explain the tradeoffs between dynamic and static process-to-processor assignment
  • Compare primary/secondary and peer architectures and identify the failure modes of each
  • Describe the four thread-scheduling strategies (load sharing, gang, dedicated, dynamic) and the workloads each is suited for

Why Don’t 8 Cores Give You 8× Speedup?

Buy a laptop with an 8-core processor and run a parallelized program. You probably won’t get 8× faster execution. You might get 4×. Sometimes less. Why?

Not all code can run in parallel. Cores share resources — memory buses, caches — that become bottlenecks under heavy load. Threads need to synchronize and wait for each other. And the OS itself, managing all of this, introduces overhead. Multiprocessor scheduling is the OS’s attempt to assign work to multiple processors as intelligently as possible — and understanding the constraints that make it genuinely hard.

Opening Discussion

Before diving in: can you name a task from everyday computing where you’d expect good parallelism? A task where you’d expect poor parallelism? What’s the difference between them? (Lead toward: embarrassingly parallel work vs. inherently sequential work.)

Types of Multiprocessor Systems

Not all multiprocessor systems are the same, and the right scheduling strategy depends on the system type.

Loosely coupled (distributed) systems are independent machines with their own memory and I/O, connected by a network. Each machine runs its own OS. Coordination happens through message passing at the application level. Cloud computing clusters are the modern example.

Functionally specialized systems have a primary general-purpose processor that offloads work to specialized processors — a GPU for graphics, a DSP for audio, a network processor for packet handling. Your phone does this. The primary controls the others and feeds them work.

Tightly coupled (SMP) systems have multiple processors sharing physical memory and running under a single OS. This is what “multicore” means in practice — your laptop’s cores share RAM and are coordinated by one kernel. SMP is dominant for everything from laptops to large servers and is the focus of this lecture.

Synchronization Granularity

Before you can schedule parallel work effectively, you need to understand how often the parallel threads communicate and synchronize. This is granularity:

Grain Size Description Sync Interval
Fine Parallelism within a single instruction stream < 20 instructions
Medium Parallel tasks within one application 20–200 instructions
Coarse Concurrent processes in a multiprogrammed environment 200–2,000 instructions
Very Coarse Distributed processes across network nodes 2,000–1M instructions
Independent Unrelated processes, no coordination N/A

Granularity matters because synchronization has overhead — locking, waiting, signaling, cache invalidation. Fine-grained parallelism (vectorized math, pipeline execution) is usually managed by hardware and compilers, not the OS. Medium-grained parallelism — parallel threads within an application — is where OS scheduling decisions make the biggest difference.

Assigning Processes to Processors

In an SMP system, the OS decides which core each process runs on. Two approaches:

Dynamic assignment treats all cores as a shared pool. Any process can run on any available core. A single global ready queue services all processors. This achieves excellent load balance and is the dominant approach in modern OSes including Linux and Windows.

Static assignment binds a process to a specific core at creation. That core’s scheduler manages it exclusively until termination. The advantage is reduced scheduling overhead and potentially better cache reuse — the process always runs on the same core, keeping its data warm. The disadvantage is load imbalance: one core can be swamped while another idles.

Architecture: Who Decides?

Two patterns govern how scheduling decisions are made across processors:

Primary/Secondary architecture: one processor handles all scheduling for the others. The secondaries request work from the primary. Simple to implement — scheduling logic lives in one place, conflicts are easy to resolve. But the primary is both a performance bottleneck (all scheduling traffic flows through one processor) and a single point of failure (if the primary crashes, the system stops).

Peer architecture: every processor runs the kernel and makes its own scheduling decisions from a shared process pool. Better scalability, no single point of failure. Significantly more complex: the OS must ensure two processors don’t pick the same process simultaneously, requiring mutual exclusion on the global ready queue — which itself becomes a contention point under heavy load. Most real SMP OSes use a peer architecture.

Board Exercise: Primary/Secondary Failure

Walk through what happens in a primary/secondary system when: (a) a secondary processor fails, (b) the primary processor fails. Compare to the same scenarios in a peer architecture. Which architecture would you choose for a hospital’s life-support monitoring system, and why?

Thread Scheduling Strategies

Processes aren’t always the unit of work on multiprocessors — often threads are. Four strategies:

Load sharing extends uniprocessor scheduling to multiple cores. A global queue of threads exists; any idle core pulls from it. Load stays balanced, no central scheduler is needed. The costs: the global queue requires mutual exclusion (contention under heavy load); preempted threads often resume on different cores (cold cache); threads from the same application rarely all run simultaneously (hurting parallelism for tightly-coupled apps).

Gang scheduling assigns a set of related threads to run simultaneously on matching cores — one thread per core, all at once. When the time slice expires, the whole gang is preempted together. This dramatically reduces synchronization overhead: if all threads in a parallel task run at the same time, they can coordinate without waiting on each other to be scheduled. Particularly valuable for scientific simulations, game engines, and parallel database queries.

Gang scheduling can be uniform (all gangs get equal time slices) or weighted (higher-priority gangs get larger slices).

Dedicated processor assignment gives each thread its own processor for the application’s entire lifetime. If a thread blocks, its processor idles. The defense: in high-performance computing with hundreds of cores, processor utilization is no longer the most important metric. If letting a processor idle during a 10ms lock wait allows the overall job to finish 5× faster by eliminating scheduling overhead, the idle time is worth it.

Dynamic scheduling lets the application vary its thread count during execution. The OS responds dynamically: when processors are idle, allocate them to requesting jobs; when a new job arrives and all processors are busy, take one processor from any job currently holding more than one; if no job has more than one processor, the new job waits. This requires cooperation between the OS and application runtime, but achieves good utilization across mixed workloads.

Discussion Prompt

A scientific simulation uses 32 threads that synchronize at a barrier every 15 instructions. A web server handles 500 independent HTTP requests per second. Which scheduling strategy would you recommend for each, and why? What would happen if you applied the wrong strategy?
