05 · Uniprocessor Scheduling

Learning Objectives

By the end of this lecture, you should be able to:

  • Explain what the three layers of scheduling (long-term, medium-term, short-term) each control
  • Calculate average wait time and turnaround time for FCFS, SJF, SRTF, and Round Robin
  • Explain the convoy effect, Belady’s Anomaly, and starvation, and which algorithms suffer from each
  • Describe why preemption is necessary for interactive systems and what race conditions it can introduce

The Problem Scheduling Solves

Imagine a single CPU and a dozen processes all wanting to run. Some are playing music — needs the CPU regularly, in short bursts, with tight timing. Some are compiling code — needs the CPU for long stretches. Some are waiting on network responses — mostly idle, short bursts of activity. If the CPU simply ran them in order of arrival, a long compilation would block music playback entirely. The user experience would be terrible.

Scheduling is the OS’s answer to: which process gets the CPU next, and for how long? The algorithm it chooses determines how responsive the system feels, how efficiently the CPU is used, and whether any process ever gets permanently starved. There’s no perfect algorithm — every design involves tradeoffs — which is why modern OSes use different schedulers for different situations.

Three Layers of Scheduling

Long-term scheduling decides which programs get admitted into the system as processes. It controls the degree of multiprogramming — how many processes exist at once. More processes means smaller slices of CPU and memory per process, but potentially higher throughput. In most desktop OSes this is implicit (every launched app just runs), but in batch and production systems it’s explicit and important.

Medium-term scheduling handles swapping — moving processes between memory and disk based on memory pressure. When memory is scarce, it suspends processes to free space; when pressure eases, it revives them. This directly controls how many processes actively compete for the CPU.

Short-term scheduling — the dispatcher — is what people usually mean by “the scheduler.” It runs extremely frequently, potentially thousands of times per second, and makes the fine-grained decision of which ready process runs next. It fires on clock interrupts, I/O completions, new arrivals to the ready queue, and whenever the current process blocks.

What Makes a Good Scheduler?

Goals differ based on who you’re optimizing for.

From the user’s perspective: turnaround time (submission to completion, relevant for batch) and response time (action to visible reaction, critical for interactive). Predictability matters too — a scheduler that’s usually 2 seconds but occasionally 30 creates a poor experience even if the average is acceptable.

From the system’s perspective: throughput (jobs completed per unit time) and processor utilization (keep the CPU busy, especially on expensive shared hardware). Fairness and priority enforcement also matter: high-priority processes should run first, and no process should be starved indefinitely.

These goals conflict. Maximizing response time for interactive processes may require preempting a long-running batch job that was making excellent throughput progress. There is no universally best scheduling algorithm — only algorithms better suited to different workloads.

Preemptive vs. Nonpreemptive Scheduling

Nonpreemptive schedulers let the running process keep the CPU until it voluntarily gives it up — by blocking on I/O, yielding, or terminating. Once selected, it runs until it stops.

Preemptive schedulers can forcibly remove the CPU from a running process — via a timer interrupt — and give it to another. Essential for interactive systems requiring predictable response times. All modern OSes (Linux, Windows, macOS) are preemptive.

The tradeoff: preemption requires a context switch with its associated overhead. Without preemption, a CPU-bound process can monopolize the CPU and starve everything else.

Preemption also introduces race conditions: Process A is halfway through updating shared data when it’s preempted. Process B runs and reads the half-modified structure. The data is inconsistent. This is exactly why shared data in concurrent programs requires synchronization — Lecture 6.

Scheduling Algorithms

First-Come, First-Served (FCFS)

Processes run in the order they arrive. Nonpreemptive. Simple to implement.

Suffers from the convoy effect: short processes stuck behind a long one inherit all of its wait time.

Board Exercise: FCFS

Three processes arrive simultaneously: P1 (burst 24ms), P2 (burst 3ms), P3 (burst 3ms).

Draw the Gantt chart, then calculate:

  • Average wait time: (0 + 24 + 27) / 3 = 17ms

Now reverse the order — P2, P3, P1 — and recalculate:

  • Average wait time: (0 + 3 + 6) / 3 = 3ms

Same work, same CPU time — but the order changes average wait from 17ms to 3ms. This is the motivation for SJF.

Shortest Job First (SJF)

Run the process with the shortest expected CPU burst next. Nonpreemptive.

SJF is provably optimal for minimizing average waiting time in nonpreemptive settings. The catch: you need to know burst lengths in advance, which typically requires estimation from historical averages.

Shortest Remaining Time First (SRTF)

The preemptive version of SJF: when a new process arrives, if its burst is shorter than the remaining time of the current process, preempt. Optimal for minimizing average wait time in the preemptive setting. Risk: starvation of long processes if short ones keep arriving.

Board Exercise: SJF vs. SRTF

Four processes:

Process Arrival Burst
P1 0 8
P2 1 4
P3 2 9
P4 3 5

Draw the Gantt chart for nonpreemptive SJF, then for SRTF (preemptive SJF). Compare average wait times. SRTF should give a lower average — why doesn’t it always win in practice?

Round Robin (RR)

Preemptive. Each process gets a fixed time quantum q (typically 10–100ms). After q elapses, the process is preempted and moved to the back of the ready queue.

With n processes and quantum q, every process gets CPU time within (n−1)q — a hard bound on wait time that FCFS and SJF don’t offer.

The choice of q dominates performance:

  • Large q → approaches FCFS (processes rarely preempted)
  • Small q → maximum responsiveness, but if q < context switch time, you spend more time switching than executing
Board Exercise: Round Robin

Three processes: P1 (burst 24ms), P2 (burst 3ms), P3 (3ms). Quantum = 4ms.

Draw the Gantt chart. Calculate average wait time and compare to FCFS from the first exercise. Which is better for the short processes? Which for the long process? (Takeaway: RR distributes wait time more fairly but may hurt overall throughput.)

Priority Scheduling

Associate a numeric priority with each process; always run the highest priority. Can be preemptive or nonpreemptive. When priorities tie, SJF or SRTF applies.

Starvation risk: low-priority processes may never run if high-priority ones keep arriving. Aging fixes this: gradually increase a process’s priority the longer it waits. Eventually, even the lowest-priority job gets scheduled.

Real-world priority tiers:

Priority Process Type
Highest Real-time (hard deadlines)
High System/kernel
Medium Interactive user
Low Batch background

Each tier can have its own queue with its own algorithm — Round Robin for interactive, FCFS for batch.

Dispatcher Latency

The dispatcher performs the actual context switch once the scheduler has chosen the next process. Dispatcher latency is the time between the selection and the process actually starting execution — it includes saving the outgoing state, loading the incoming state, and the cache cold-start penalty. Minimizing dispatcher latency is a kernel implementation concern, separate from the scheduling algorithm itself.

Discussion Prompt

SJF gives the best average waiting time, so why don’t all OSes use it? Think through: what does the OS actually know at scheduling time? What would happen to long jobs on a busy server that runs SJF? What does “optimal” mean here, and for whom?
