06 · Concurrency & Mutual Exclusion

Learning Objectives

By the end of this lecture, you should be able to:

  • Explain what a race condition is and demonstrate one with a concrete example
  • State the three requirements for a correct critical section solution
  • Walk through Peterson’s Algorithm and verify it meets all three requirements
  • Explain the difference between test-and-set and compare-and-swap
  • Describe when to use a spinlock vs. a blocking mutex, and when to use a semaphore over a mutex

Start Here: A Broken Program

Two threads, each incrementing a shared counter 1,000,000 times. Expected result: 2,000,000. Let’s see what actually happens:

#include <stdio.h>
#include <pthread.h>

int counter = 0;

void *increment(void *arg) {
    for (int i = 0; i < 1000000; i++)
        counter++;    // not as innocent as it looks
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);
}
Class Activity: Run It

Compile with gcc -pthread broken_counter.c -o broken_counter and run it several times. Note the results. Expected: 2,000,000. What do you actually get? Does the result change between runs? This is a race condition, and understanding exactly why it happens is the entire point of this lecture.

Why counter++ Is Not One Operation

counter++ looks like a single step. At the machine level, it isn’t:

  1. Load the current value from memory into a register
  2. Add 1 to the register
  3. Store the result back to memory

If two threads execute these steps concurrently and their steps interleave, one increment can silently overwrite the other:

Board Exercise: Trace the Race

Thread 1 and Thread 2 both try to increment counter from 42. Trace through this interleaving:

Thread 1: LOAD  counter → register1 = 42
Thread 2: LOAD  counter → register2 = 42   (reads before T1 stores!)
Thread 1: ADD   register1 = 43
Thread 2: ADD   register2 = 43
Thread 1: STORE counter = 43
Thread 2: STORE counter = 43               (overwrites T1's result!)

Result: counter = 43, not 44. One increment was lost.

Now trace an interleaving that produces the correct result. Now trace one that produces the maximum possible loss. (This last one reveals that with 1,000,000 iterations each, the minimum possible result is 1,000,000 — why?)

Race conditions are timing-dependent. They may not appear in testing (if threads don’t interleave badly), may appear rarely in production, and may disappear when you add print statements that change timing. This makes them among the hardest bugs to diagnose.

Critical Sections

The counter++ code is a critical section: code that accesses shared data and must not execute concurrently. The problem isn’t sharing — sharing is useful. The problem is that some operations on shared data require exclusive access to be correct.

The general structure:

while (true) {
    [entry section]      // request permission to enter
    critical section     // exclusive access to shared data
    [exit section]       // signal that you're done
    remainder section    // can run concurrently
}

Any correct solution must satisfy three requirements:

  1. Mutual exclusion — if Pi is in its CS, no other process is in its CS simultaneously
  2. Progress — if no process is in its CS and some want to enter, a decision is made in finite time; it cannot be postponed indefinitely
  3. Bounded waiting — a process waiting to enter its CS will eventually get in; there’s an upper bound on how many times others can enter first

All three matter. A solution achieving only mutual exclusion might deadlock (violates progress). A solution achieving mutual exclusion and progress might starve one process indefinitely (violates bounded waiting).

Software Solutions

Solution 1: Shared Turn Variable

int turn = i;
while (true) {
    while (turn != i);      // busy-wait
    /* critical section */
    turn = j;
    /* remainder */
}

Mutual exclusion? Yes — turn is either i or j, not both. Progress? No — if Pi doesn’t want the CS, Pj must still wait for Pi to set turn = j, even though Pi isn’t using the CS. Bounded waiting? Yes.

Solution 2: Flag Array

bool flag[2] = {false, false};
while (true) {
    while (flag[j]);        // wait while other is in CS
    flag[i] = true;
    /* critical section */
    flag[i] = false;
    /* remainder */
}

Mutual exclusion? No — both threads can pass the while check before either sets its flag. The check and the set are two separate steps; the world can change between them.

Solution 3: Peterson’s Algorithm

Combine both: turn for tiebreaking, flag for intent.

int turn;
bool flag[2] = {false, false};
while (true) {
    flag[i] = true;                       // declare intent
    turn = j;                             // yield priority to j
    while (flag[j] && turn == j);         // wait only if j wants in AND has priority
    /* critical section */
    flag[i] = false;
    /* remainder */
}
Board Exercise: Verify Peterson’s

Walk through all three requirements:

Mutual exclusion: Pi enters CS only when flag[j] == false OR turn == i. Can both be false simultaneously? Work through the case where both threads reach the while at the same time.

Progress: if Pj doesn’t want the CS (flag[j] == false), what happens to Pi’s while condition? Pi proceeds immediately — progress satisfied.

Bounded waiting: after Pi sets flag[i] = true and turn = j, Pi waits at most one CS entry by Pj before getting in. Verify this by tracing both threads through two full iterations.

Peterson’s and Modern Hardware

Peterson’s algorithm is correct in a sequentially consistent model, but modern CPUs and compilers reorder instructions for performance. flag[i] = true and turn = j might be reordered, breaking the algorithm. The fix is memory barriers — CPU instructions that prevent reordering across them. This illustrates why correct concurrent programming is hard even when your algorithm is right on paper.

Hardware Solutions

Modern CPUs provide atomic instructions specifically for synchronization, making correct mutual exclusion straightforward.

Test-and-Set atomically reads a boolean and sets it to true, returning the original value — indivisible:

while (test_and_set(&lock));  // spin until lock was false (acquired)
/* critical section */
lock = false;

Compare-and-Swap (CAS) atomically checks if a value equals an expected value and, if so, replaces it. Returns the original value regardless:

while (compare_and_swap(&lock, 0, 1) != 0);  // spin until lock was 0
/* critical section */
lock = 0;

CAS is the foundation of most lock-free data structures. Java’s AtomicInteger, C++11’s std::atomic, and Rust’s std::sync::atomic all expose it.

Mutex Locks and Semaphores

A mutex is the standard OS abstraction for protecting a critical section — a binary lock with acquire() and release():

while (true) {
    acquire lock
    critical section
    release lock
    remainder section
}

The version above uses busy waiting (spinning) — the thread loops checking the lock. A spinlock is appropriate when the wait will be very short (shorter than a context switch). For longer waits, the OS can block the thread and schedule something else.

Mutex in C: Fixing the Broken Counter

The POSIX threads library provides pthread_mutex_t. Here is the broken counter from the opening of this lecture, corrected with a mutex:

#include <stdio.h>
#include <pthread.h>

int counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;  // declare and initialize

void *increment(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&lock);    // acquire — blocks if another thread holds it
        counter++;                    // critical section: safe now
        pthread_mutex_unlock(&lock);  // release — wakes a waiting thread
    }
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);  // always 2000000
    pthread_mutex_destroy(&lock);
}

Compile with gcc -pthread mutex_counter.c -o mutex_counter. Every run now produces exactly 2,000,000. The cost: two function calls per iteration (lock and unlock) plus the blocking overhead when threads contend.

Common Mutex Mistakes

Three bugs that will ruin your day:

Forgetting to unlock — if a thread exits its critical section via an early return or a goto, it may skip pthread_mutex_unlock. Every code path out of the critical section must release the lock.

Locking the wrong mutex — if you have two mutexes protecting two different data structures, accidentally locking mutex_a around data structure B gives you zero protection and no error message.

Double-locking — pthread_mutex_lock on a mutex the same thread already holds will deadlock that thread forever. Use pthread_mutex_trylock if you need non-blocking acquisition.

A More Realistic Mutex Example: Shared Bank Account

Real code rarely just increments a counter. Here is a shared bank account where two threads — one depositing, one withdrawing — must not interfere with each other:

#include <stdio.h>
#include <pthread.h>

typedef struct {
    double balance;
    pthread_mutex_t lock;
} Account;

void deposit(Account *acct, double amount) {
    pthread_mutex_lock(&acct->lock);
    acct->balance += amount;
    printf("Deposited %.2f, balance: %.2f\n", amount, acct->balance);
    pthread_mutex_unlock(&acct->lock);
}

void withdraw(Account *acct, double amount) {
    pthread_mutex_lock(&acct->lock);
    if (acct->balance >= amount) {
        acct->balance -= amount;
        printf("Withdrew  %.2f, balance: %.2f\n", amount, acct->balance);
    } else {
        printf("Insufficient funds (balance: %.2f)\n", acct->balance);
    }
    pthread_mutex_unlock(&acct->lock);
}

void *depositor(void *arg) {
    Account *acct = (Account *)arg;
    for (int i = 0; i < 5; i++) deposit(acct, 100.0);
    return NULL;
}

void *withdrawer(void *arg) {
    Account *acct = (Account *)arg;
    for (int i = 0; i < 5; i++) withdraw(acct, 80.0);
    return NULL;
}

int main() {
    Account acct = {500.0, PTHREAD_MUTEX_INITIALIZER};
    pthread_t t1, t2;
    pthread_create(&t1, NULL, depositor,  &acct);
    pthread_create(&t2, NULL, withdrawer, &acct);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("Final balance: %.2f\n", acct.balance);
    pthread_mutex_destroy(&acct.lock);
}

Notice that the mutex is part of the struct — this is a common C pattern. The lock travels with the data it protects, which makes it much harder to accidentally protect the wrong thing.

Semaphores

A semaphore generalizes the mutex. Where a mutex is binary, a semaphore has an integer value representing a count of available resources. Two atomic operations:

  • sem_wait(S) — decrements S; if S becomes negative, the calling process blocks
  • sem_post(S) — increments S; if processes are blocked on S, wake one

A binary semaphore (value 0 or 1) behaves like a mutex. A counting semaphore controls access to a resource pool — for example, limiting simultaneous database connections to exactly 10.

Semaphore in C: Signaling Between Threads

POSIX semaphores (semaphore.h) come in two varieties: unnamed (between threads in the same process) and named (between separate processes). For thread-level synchronization, use sem_init:

#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

// Producer/consumer: producer must run before consumer can proceed
sem_t ready;   // signals that data is ready

int data = 0;

void *producer(void *arg) {
    printf("Producer: preparing data...\n");
    data = 42;                  // write the shared data
    printf("Producer: data ready.\n");
    sem_post(&ready);           // signal consumer: go ahead
    return NULL;
}

void *consumer(void *arg) {
    sem_wait(&ready);           // block until producer signals
    printf("Consumer: received data = %d\n", data);
    return NULL;
}

int main() {
    sem_init(&ready, 0, 0);    // initial value 0: consumer blocks immediately

    pthread_t prod, cons;
    pthread_create(&cons, NULL, consumer, NULL);  // start consumer first...
    pthread_create(&prod, NULL, producer, NULL);  // ...producer may run later

    pthread_join(prod, NULL);
    pthread_join(cons, NULL);
    sem_destroy(&ready);
}

Compile with gcc -pthread semaphore_signal.c -o semaphore_signal. The consumer thread always waits for the producer, regardless of scheduling order. Try swapping the pthread_create order — it still works correctly. This is ordering enforcement, something a mutex alone cannot do.

Board Exercise: Mutex vs. Semaphore

For each scenario, decide whether you’d reach for a mutex or a semaphore — and why:

  1. You have a linked list shared between 4 threads. Any thread might insert or delete nodes.
  2. A logging thread must print output only after a worker thread finishes its computation.
  3. A server handles up to 10 simultaneous database queries; the 11th request must wait until one finishes.
  4. Two threads share a variable. Thread A writes it; Thread B reads it. You need to ensure B never reads a partial write.

(Key insight: mutexes protect shared data from concurrent access. Semaphores can do that too, but their real power is signaling — coordinating the order in which things happen.)

Counting Semaphore: Bounding a Resource Pool

Here is a counting semaphore limiting simultaneous access to a pool of database connections:

#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>
#include <unistd.h>

#define MAX_CONNECTIONS 3
#define NUM_THREADS     8

sem_t db_slots;   // counting semaphore: how many connections are free

void *use_database(void *arg) {
    int id = *(int *)arg;

    printf("Thread %d: waiting for a connection...\n", id);
    sem_wait(&db_slots);               // decrement; block if 0 slots remain

    printf("Thread %d: connected. Running query.\n", id);
    sleep(1);                          // simulate query time
    printf("Thread %d: done. Releasing connection.\n", id);

    sem_post(&db_slots);               // increment; wake a waiting thread
    return NULL;
}

int main() {
    sem_init(&db_slots, 0, MAX_CONNECTIONS);  // start with 3 available slots

    pthread_t threads[NUM_THREADS];
    int ids[NUM_THREADS];

    for (int i = 0; i < NUM_THREADS; i++) {
        ids[i] = i + 1;
        pthread_create(&threads[i], NULL, use_database, &ids[i]);
    }
    for (int i = 0; i < NUM_THREADS; i++)
        pthread_join(threads[i], NULL);

    sem_destroy(&db_slots);
}

Run this and watch the output: exactly 3 threads run concurrently at any time. Threads 4–8 wait until a slot opens. The semaphore’s integer value tracks available resources — no manual bookkeeping required.

Practice 1 — Mutex: Thread-Safe Stack

A stack implemented with an array is not thread-safe. Multiple threads pushing and popping simultaneously will corrupt the top index.

Your task: complete the push and pop functions so the stack is safe under concurrent access.

#include <stdio.h>
#include <pthread.h>
#include <stdlib.h>

#define STACK_SIZE 64
#define NUM_THREADS 4
#define OPS_PER_THREAD 10

typedef struct {
    int data[STACK_SIZE];
    int top;
    pthread_mutex_t lock;
} Stack;

Stack stack = { .top = -1, .lock = PTHREAD_MUTEX_INITIALIZER };

void push(int val) {
    // TODO: acquire the lock, check for overflow,
    //       push val, release the lock
}

int pop() {
    // TODO: acquire the lock, check for underflow (return -1 if empty),
    //       pop and return the value, release the lock
    return -1;
}

void *worker(void *arg) {
    int id = *(int *)arg;
    for (int i = 0; i < OPS_PER_THREAD; i++) {
        push(id * 100 + i);
        int val = pop();
        if (val != -1)
            printf("Thread %d popped: %d\n", id, val);
    }
    return NULL;
}

int main() {
    pthread_t threads[NUM_THREADS];

    for (int i = 0; i < NUM_THREADS; i++) {

Verify your solution: the program should never crash or report a top outside [−1, STACK_SIZE−1]. Run it under Valgrind’s helgrind tool (valgrind --tool=helgrind ./stack) — a correct solution produces no data-race warnings.

Practice 2 — Mutex: Histogram with Multiple Threads

Eight threads each roll a six-sided die 10,000 times and record results in a shared histogram array. Without synchronization the counts will be wrong.

#include <stdio.h>
#include <pthread.h>
#include <stdlib.h>
#include <time.h>

#define NUM_THREADS 8
#define ROLLS_EACH  10000

int histogram[7] = {0};           // index 1-6; index 0 unused
pthread_mutex_t hist_lock = PTHREAD_MUTEX_INITIALIZER;

void *roll_dice(void *arg) {
    // Each thread needs its own random seed to avoid correlation.
    unsigned int seed = (unsigned int)(size_t)arg ^ (unsigned int)time(NULL);
    for (int i = 0; i < ROLLS_EACH; i++) {
        int face = (rand_r(&seed) % 6) + 1;
        // TODO: protect histogram[face]++ with the mutex
        histogram[face]++;   // <-- race condition here; fix it
    }
    return NULL;
}

int main() {
    pthread_t threads[NUM_THREADS];
    for (long i = 0; i < NUM_THREADS; i++)
        pthread_create(&threads[i], NULL, roll_dice, (void *)i);
    for (int i = 0; i < NUM_THREADS; i++)
        pthread_join(threads[i], NULL);

    int total = 0;
    for (int f = 1; f <= 6; f++) {
        printf("Face %d: %d\n", f, histogram[f]);
        total += histogram[f];
    }
    printf("Total rolls: %d (expected %d)\n", total, NUM_THREADS * ROLLS_EACH);
    pthread_mutex_destroy(&hist_lock);
}

Expected output: Total rolls should always equal exactly 80,000. Without the fix, it will frequently be less.

Extension: instead of one global mutex, try giving each histogram bucket its own mutex (pthread_mutex_t bucket_lock[7]). Does it change performance? Does it change correctness?

Practice 3 — Semaphore: Print in Order

Three threads print messages, but they must always appear in order: Thread A first, then B, then C — regardless of which thread the scheduler runs first.

#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

sem_t a_done;   // posted when A finishes; B waits on this
sem_t b_done;   // posted when B finishes; C waits on this

void *thread_a(void *arg) {
    // TODO: print "Thread A running", then signal B to proceed
    printf("Thread A running\n");
    return NULL;
}

void *thread_b(void *arg) {
    // TODO: wait for A's signal, print "Thread B running", then signal C
    printf("Thread B running\n");
    return NULL;
}

void *thread_c(void *arg) {
    // TODO: wait for B's signal, print "Thread C running"
    printf("Thread C running\n");
    return NULL;
}

int main() {
    sem_init(&a_done, 0, 0);
    sem_init(&b_done, 0, 0);

    pthread_t ta, tb, tc;
    // Intentionally create in reverse order — your semaphores must enforce ordering
    pthread_create(&tc, NULL, thread_c, NULL);
    pthread_create(&tb, NULL, thread_b, NULL);
    pthread_create(&ta, NULL, thread_a, NULL);

    pthread_join(ta, NULL);
    pthread_join(tb, NULL);
    pthread_join(tc, NULL);

    sem_destroy(&a_done);
    sem_destroy(&b_done);
}

Expected output (always, on every run):

Thread A running
Thread B running
Thread C running

Practice 4 — Semaphore: Classic Producer/Consumer

A producer generates integers and places them in a bounded buffer; a consumer removes and prints them. Without coordination the producer can overflow the buffer and the consumer can read from an empty one.

This exercise requires three synchronization objects:

  • sem_t empty — counts free slots (initialized to BUFFER_SIZE)
  • sem_t full — counts filled slots (initialized to 0)
  • pthread_mutex_t mutex — protects the buffer index during access
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

#define BUFFER_SIZE 5
#define NUM_ITEMS   20

int buffer[BUFFER_SIZE];
int in  = 0;   // next slot to write
int out = 0;   // next slot to read

sem_t empty;
sem_t full;
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

void *producer(void *arg) {
    for (int item = 1; item <= NUM_ITEMS; item++) {
        // TODO:
        // 1. sem_wait on empty  (wait for a free slot)
        // 2. lock the mutex
        // 3. write item into buffer[in], advance in = (in+1) % BUFFER_SIZE
        // 4. unlock the mutex
        // 5. sem_post on full   (signal that a new item is ready)
        printf("Produced: %d\n", item);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < NUM_ITEMS; i++) {
        // TODO:
        // 1. sem_wait on full   (wait for an available item)
        // 2. lock the mutex
        // 3. read buffer[out], advance out = (out+1) % BUFFER_SIZE
        // 4. unlock the mutex
        // 5. sem_post on empty  (signal that a slot is now free)
        printf("Consumed: (fill this in)\n");
    }
    return NULL;
}

int main() {
    sem_init(&empty, 0, BUFFER_SIZE);
    sem_init(&full,  0, 0);

    pthread_t prod, cons;
    pthread_create(&prod, NULL, producer, NULL);
    pthread_create(&cons, NULL, consumer, NULL);
    pthread_join(prod, NULL);
    pthread_join(cons, NULL);

    sem_destroy(&empty);
    sem_destroy(&full);
    pthread_mutex_destroy(&mutex);
}

Expected behavior: every integer 1–20 is produced and consumed exactly once, in order. The buffer never holds more than BUFFER_SIZE items simultaneously.

Key question: what happens if you remove mutex and rely only on the two semaphores? Is it still correct with one producer and one consumer? What breaks when you add a second producer?

Practice 5 — Challenge: Readers/Writers Lock

Multiple reader threads may read a shared value simultaneously. A writer thread needs exclusive access — no readers or other writers. This is the readers/writers problem.

The rules: - Any number of readers may read concurrently. - A writer must wait until all current readers finish. - No new readers may start while a writer is waiting or writing.

#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>
#include <unistd.h>

#define NUM_READERS 5
#define NUM_WRITERS 2

int shared_data = 0;
int reader_count = 0;

pthread_mutex_t count_lock = PTHREAD_MUTEX_INITIALIZER;  // protects reader_count
sem_t           write_lock;                               // exclusive writer access

void *reader(void *arg) {
    int id = *(int *)arg;
    for (int i = 0; i < 3; i++) {
        // TODO: entry — increment reader_count; if first reader, wait on write_lock
        printf("Reader %d: shared_data = %d\n", id, shared_data);
        // TODO: exit  — decrement reader_count; if last reader, post write_lock
        usleep(100000);
    }
    return NULL;
}

void *writer(void *arg) {
    int id = *(int *)arg;
    for (int i = 0; i < 2; i++) {
        // TODO: wait on write_lock, write, post write_lock
        shared_data++;
        printf("Writer %d: wrote shared_data = %d\n", id, shared_data);
        usleep(200000);
    }
    return NULL;
}

int main() {
    sem_init(&write_lock, 0, 1);

    pthread_t readers[NUM_READERS], writers[NUM_WRITERS];
    int rids[NUM_READERS], wids[NUM_WRITERS];

    for (int i = 0; i < NUM_READERS; i++) { rids[i] = i+1; pthread_create(&readers[i], NULL, reader, &rids[i]); }
    for (int i = 0; i < NUM_WRITERS; i++) { wids[i] = i+1; pthread_create(&writers[i], NULL, writer, &wids[i]); }
    for (int i = 0; i < NUM_READERS; i++) pthread_join(readers[i], NULL);
    for (int i = 0; i < NUM_WRITERS; i++) pthread_join(writers[i], NULL);

    sem_destroy(&write_lock);
    pthread_mutex_destroy(&count_lock);
}

Hint: the classic entry protocol is:

pthread_mutex_lock(&count_lock);
reader_count++;
if (reader_count == 1) sem_wait(&write_lock);  // first reader blocks writers
pthread_mutex_unlock(&count_lock);

Follow-up questions: Does this solution favor readers or writers? What could happen to writers under heavy read load? How would you modify it to give writers priority?
