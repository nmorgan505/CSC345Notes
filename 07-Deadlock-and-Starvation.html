07 · Deadlock & Starvation

Learning Objectives

By the end of this lecture, you should be able to:

  • State the four necessary and sufficient conditions for deadlock
  • Detect deadlock using a resource allocation graph
  • Explain the Banker’s Algorithm and evaluate a state as safe or unsafe
  • Compare prevention, avoidance, and detection/recovery strategies and identify when each is appropriate

Four Cars at a Four-Way Stop

Four cars arrive at a four-way stop simultaneously. Each one needs to cross, and each can only proceed when the opposing traffic clears. But each car is also blocking the opposing traffic for one of the others. Nobody moves. Nobody will ever move. This is deadlock.

In computing: a set of processes where each one is waiting for a resource held by another, and none can ever proceed without external intervention. Deadlock is not a crash — the processes are alive and technically “running,” just permanently suspended waiting for something that will never happen. It’s often harder to detect than a crash for exactly this reason.

Opening Activity: The Dining Philosophers

Five philosophers sit at a round table with a bowl of rice in the middle. Between each pair of neighbors lies one chopstick. To eat, a philosopher needs both adjacent chopsticks. They alternate between thinking (needs nothing) and eating (needs two chopsticks).

Before I explain anything: in small groups, try to design a rule set that lets all five philosophers eat eventually, with no deadlock and no starvation. You have 3 minutes.

We’ll compare solutions after discussing the formal conditions.

The Four Necessary Conditions

Deadlock can only arise if all four conditions hold simultaneously. Remove any one and deadlock is impossible.

Mutual exclusion: at least one resource must be held exclusively — only one process can use it at a time. Most I/O devices, write-mode file locks, and mutexes are mutually exclusive by design.

Hold and wait: a process holds at least one resource while waiting for additional resources held by others. The dangerous pattern: acquire A, then try to acquire B while still holding A.

No preemption: resources cannot be forcibly taken away. A process releases resources only voluntarily when done with them. You can’t just yank a lock out of a process’s hands.

Circular wait: there exists a circular chain {P0, P1, …, Pn} where P0 waits for a resource held by P1, P1 waits for one held by P2, …, and Pn waits for one held by P0.

Board Exercise: Identify the Conditions

Two processes, two semaphores:

Process P1:      Process P2:
  semWait(s1)      semWait(s2)
  semWait(s2)      semWait(s1)

P1 acquires s1, P2 acquires s2, then each tries for the other’s semaphore.

Identify which of the four conditions is satisfied in this scenario. Which condition would you eliminate to prevent the deadlock, and what would that change about the code?

Resource Allocation Graphs

A resource allocation graph visualizes deadlock conditions. Processes are circles; resources are rectangles (dots inside represent instances). An arrow from process to resource means “waiting for”; an arrow from resource to process means “allocated to.”

Key rules:

  • No cycle → no deadlock possible
  • Cycle, one instance per resource type → deadlock
  • Cycle, multiple instances per resource type → possible deadlock, needs further analysis

The diagrams below use dashed arrows (→ ·· ·→) for request edges and solid arrows (→) for assignment edges.

Example 1: No Cycle — No Deadlock

P1 holds R1 and is waiting for R2. P2 holds R2 and is not waiting for anything. There is no cycle: following the arrows never brings you back to where you started.

P2 can finish and release R2 at any time — P1 is merely waiting, not deadlocked. The system will make progress.

Example 2: Cycle with Single-Instance Resources — Deadlock

P1 holds R1 and requests R2. P2 holds R2 and requests R1. Each is waiting for the other to release something neither will ever release.

Trace the cycle: P1 → R2 → P2 → R1 → P1. Every node in the cycle is permanently blocked. This is the deadlock from the semaphore example earlier in the lecture with s1/s2.

Example 3: Cycle with Multi-Instance Resources — Not Necessarily Deadlock

R1 has two instances. P1 holds one instance of R1 and requests R2. P2 holds R2 and requests R1. P3 holds the other instance of R1 and needs nothing else.

There is a cycle (P1 → R2 → P2 → R1 → P1), but it is not a deadlock. P3 holds R1 instance 2 and isn’t waiting for anything — P3 can finish and release its instance. That frees R1 for P2, which can then finish and release R2, which unblocks P1. The safe sequence is P3 → P2 → P1.

The key lesson: a cycle is a necessary condition for deadlock with single-instance resources, but not sufficient when resources have multiple instances.

Example 4: Three Processes — Deadlock Detection Exercise

This is the graph you should be able to draw and analyze from scratch:

  • P1 holds R2, requests R1
  • P2 holds nothing, requests R1 and R2 (it has requested both but neither is granted yet — R1 has one instance, R2 has one instance, both are held)
  • P3 holds R1, requests R2

Two cycles exist here: P1 → R1 → P3 → R2 → P1, and P2 → R1 → P3 → R2 → P2. Since both resources have only one instance, both cycles confirm deadlock. P1, P2, and P3 are all permanently blocked.

Board Exercise: Draw the Graph

Draw the resource allocation graph for the semaphore example above (P1 holds s1/requests s2, P2 holds s2/requests s1). Does it contain a cycle? Now add a third semaphore s3 and a third process P3 that holds s3 and waits for s1. Add P1 also wanting s3. Is the system now definitely deadlocked, or only possibly?

Strategies for Handling Deadlock

Three fundamentally different approaches, each suitable for different situations.

Prevention: Make One Condition Impossible

Design the system so at least one necessary condition can never hold. This is conservative but guarantees no deadlock.

Attacking mutual exclusion — generally impossible for devices and write locks. Some resources (read-only data, immutable files) are inherently shareable, but most aren’t.

Attacking hold-and-wait — require processes to request all resources upfront before execution begins. If they can’t get everything immediately, they get nothing and wait. Eliminates hold-and-wait but is deeply impractical: most programs can’t enumerate all their resource needs before running, and early-acquiring resources wastes them.

Attacking no preemption — allow the OS to forcibly reclaim resources. If P1 holds A and requests B but B is unavailable, take A away; P1 restarts from scratch. Works for CPU registers and memory pages; doesn’t work for half-written files or in-progress I/O.

Attacking circular wait — impose a global ordering on resource types and require every process to request in that order. If all processes must request R1 before R2 before R3, no circular chain can form. This is practical and widely used: Linux kernel developers follow strict documented lock-ordering conventions specifically to prevent deadlock in kernel code.

Avoidance: Never Enter an Unsafe State

Allow the four conditions but refuse resource requests that might lead to deadlock. Requires knowing processes’ maximum resource needs upfront.

A state is safe if there exists at least one sequence in which all processes can finish. The OS checks before each allocation: does a safe ordering still exist after this grant? If yes, grant it. If no, deny and make the process wait.

The Banker’s Algorithm is the classical avoidance approach, named for how a bank manages loan risk. It uses four data structures:

  • Available[j] — how many instances of resource Rj are currently free
  • Max[i][j] — the maximum instances of Rj that process Pi might ever request
  • Allocation[i][j] — instances of Rj currently held by Pi
  • Need[i][j] = Max[i][j] - Allocation[i][j] — remaining potential requests from Pi
Board Exercise: Banker’s Algorithm Safety Check

5 processes (P0–P4), 3 resource types (A: 10, B: 5, C: 7 total).

Allocation:

A B C
P0 0 1 0
P1 2 0 0
P2 3 0 2
P3 2 1 1
P4 0 0 2

Max:

A B C
P0 7 5 3
P1 3 2 2
P2 9 0 2
P3 2 2 2
P4 4 3 3

Available: (3, 3, 2) — remaining after all allocations.

  1. Calculate Need for each process
  2. Find a process whose Need ≤ Available; run it (simulate completion, release resources)
  3. Repeat until all processes finish or no process can proceed

Is this state safe? If so, what is the safe sequence?

(Answer: P1 can run first with (3,3,2). After P1 releases, Available becomes (5,3,2). Then P3, P4, P0, P2 — safe sequence exists.)

The Banker’s Algorithm’s limitation: it requires knowing maximum resource needs in advance, assumes a fixed set of processes and resources, and is impractical for most real applications. It’s elegant as a design principle; real OSes rarely implement it directly.

Detection and Recovery: Let It Happen, Then Break It

Allow deadlock to occur. Periodically check for it. When found, break it. This is common for resources that can’t easily be made preemptible or for systems where deadlock is rare.

Detection requires cycle detection in the resource allocation graph (for single-instance resources) or a matrix algorithm similar to the Banker’s (for multiple instances). Check frequency is a design decision: more frequent checks find deadlocks faster but consume CPU.

Process termination recovery: kill one or more deadlocked processes to break the cycle. Choose which to kill based on priority, runtime so far, resources held, and impact on other processes. Aborting all deadlocked processes is simple but brutal; aborting one at a time is surgical but requires re-running detection after each.

Resource preemption recovery: forcibly take a resource from one process and give it to another. The victim process rolls back to a checkpoint. Risk: the same process may be repeatedly victimized (starvation at the recovery level). Fix: include rollback count in the victim-selection cost function.

Discussion Prompt

Return to the dining philosophers solutions your groups proposed at the start. Classify each solution: does it use prevention (which condition?), avoidance, or detection/recovery? Does it guarantee no starvation as well as no deadlock? Which solution would you actually implement in production code, and why?
