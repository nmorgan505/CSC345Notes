08 · Memory Management

Learning Objectives

By the end of this lecture, you should be able to:

  • Explain virtual memory and why every process gets its own address space
  • Describe how paging eliminates external fragmentation and how address translation works
  • Trace through a page fault and explain its performance impact using the EAT formula
  • Compare FIFO, OPT, and LRU page replacement algorithms and explain Belady’s Anomaly
  • Explain the causes of thrashing and the OS response
  • Calculate disk access times and compare FCFS, SCAN, C-SCAN, and SSTF scheduling

Your Program Is Living in a Lie

When your C program accesses memory address 0x7fff5a2b3c40, it is not touching physical RAM at that address. In fact, two different processes running simultaneously might both use that exact address — and that’s fine, because neither is touching the same physical memory.

Your program operates inside a virtual address space: a fiction the OS maintains, mapping the addresses your program sees to wherever data actually lives in physical RAM (or on disk if swapped out). Every process gets its own complete virtual address space, starting at address 0. The mapping is managed transparently by OS and hardware — your program never has to think about it.

This illusion explains a lot: why programs can be larger than physical RAM, why one crashing process doesn’t corrupt another, why adding RAM makes the system faster, and why malloc can fail.

Opening Discussion

Before we explain virtual memory: on a 64-bit system, every process “sees” up to 2^64 bytes of address space. A 64-bit machine might have 16GB of physical RAM. How can dozens of processes each claim they have 2^64 bytes available? What has to be true about how they use that space for this to work?

Requirements of Memory Management

Memory management must balance five competing demands simultaneously:

Relocation: a process doesn’t know in advance where it will be loaded. Different runs might land at entirely different physical addresses. All memory references must be translated correctly regardless.

Protection: a process must never access another process’s memory. The hardware checks every access — a significant ongoing cost for a critical safety property.

Sharing: processes should sometimes share memory — multiple instances of the same program can share code, and cooperative processes can share data. This requires controlled sharing without compromising protection elsewhere.

Logical organization: programs have structure (code, stack, heap, data). The memory model should reflect this rather than forcing everything into a flat uniform space.

Physical organization: programmers shouldn’t manage what’s in RAM vs. on disk. The OS handles this transparently.

Fixed and Dynamic Partitioning: Why They Failed

Early OSes divided physical memory into partitions — lessons from both approaches explain why virtual memory was necessary.

Fixed partitioning split RAM into static regions at boot. One process per partition. Problems: small processes in large partitions wasted space (internal fragmentation); large processes that didn’t fit couldn’t run; partition count limited multiprogramming.

Dynamic partitioning allocated exactly the memory each process needed. Eliminated internal fragmentation but created external fragmentation: as processes came and went at different sizes, memory filled with small unusable gaps. Compaction — moving processes to consolidate free space — was the fix, but it was expensive and disruptive.

Three placement algorithms emerged for dynamic partitioning: first-fit (use the first gap large enough), best-fit (use the smallest gap that fits, minimizing waste), next-fit (like first-fit but start from the last allocated point, spreading allocations throughout memory).

Paging: The Solution That Stuck

Paging breaks both physical memory and the process’s virtual address space into fixed-size chunks of equal size — typically 4KB on modern systems. Physical chunks are frames; virtual chunks are pages.

The key insight: pages need not map to contiguous frames. Page 0 of your program might be in physical frame 47, page 1 in frame 2, page 3 in frame 891. The page table — maintained by the OS for each process — records this mapping. Address translation is done transparently by hardware (the Memory Management Unit, or MMU).

Address translation: a virtual address is split into a page number (high bits, index into the page table) and a page offset (low bits, byte position within the page). The page table maps page number → frame number. Physical address = frame_number × page_size + offset.

Board Exercise: Address Translation

Page size: 1KB (= 1024 bytes). Virtual address bits: 16 (so 6 bits page offset, 10 bits page number).

Given page table: page 0 → frame 3, page 1 → frame 7, page 2 → frame 1, page 3 → frame 5.

Translate these virtual addresses to physical: 1. Virtual address 1000 → page 0, offset 1000 → physical: 3×1024 + 1000 = 4072 2. Virtual address 1500 → page 1, offset 476 → physical: 7×1024 + 476 = 7644 3. Virtual address 3000 → page 2, offset 952 → physical: 1×1024 + 952 = 1976

(Paging eliminates external fragmentation entirely — why? Because any free frame can hold any page, regardless of size.)

Virtual Memory: Running Programs Larger Than RAM

Paging enables something powerful: a page doesn’t need to be in physical RAM. It can live on disk, loaded only when the process actually accesses it. This is demand paging — the foundation of virtual memory.

Each page table entry has a valid/invalid bit: valid means the page is in RAM; invalid means it’s on disk or not yet allocated. When a process accesses an invalid page, the hardware generates a page fault. The OS handles it:

  1. Trap to the OS, save registers and process state
  2. Confirm it was a page fault; find the page’s location on disk
  3. Find a free frame (evicting a page if necessary)
  4. Initiate a disk read into that frame
  5. Schedule another process while waiting for disk I/O
  6. When the disk read completes, update the page table; resume the faulting process

The process never knows any of this happened. The memory access just took longer.

Effective Access Time (EAT): if p is the page fault rate, then:

EAT = (1 − p) × memory_access_time + p × page_fault_overhead

If memory access takes 100ns and a page fault takes 10ms, even a 0.1% fault rate increases average access time dramatically. Minimizing page fault rate is essential.

Copy-on-Write (COW): when fork() is called, the child and parent initially share the parent’s physical pages (marked read-only). Only when either process writes to a page does the OS create a private copy for the writer. Most fork/exec pairs never write to inherited pages — COW makes those forks nearly free.

Page Replacement Algorithms

When a page fault occurs and no free frames exist, the OS must evict a page. The choice affects performance significantly.

FIFO: evict the oldest page. Simple. Suffers from Belady’s Anomaly — adding more frames can increase page faults for some reference patterns. This counterintuitive result disqualifies FIFO from serious use.

Optimal (OPT): evict the page not needed for the longest time in the future. Minimizes page faults provably. Impossible to implement (requires future knowledge). Used as a benchmark.

Least Recently Used (LRU): evict the page not accessed for the longest time. Uses the past as a proxy for the future — reasonable given locality of reference. Performs close to OPT in practice. Does not suffer Belady’s Anomaly. Implementation challenge: tracking recency without checking timestamps on every access.

Board Exercise: Page Replacement

Reference string: 7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1

With 3 frames, calculate the number of page faults under: 1. FIFO 2. LRU 3. OPT

Compare the three. Notice that OPT serves as the theoretical minimum. How close does LRU get?

(Also try FIFO with 4 frames and note if Belady’s Anomaly appears — does adding a frame ever increase* page faults for this string?)*

Thrashing occurs when the OS spends more time swapping pages in and out than executing useful code. It happens when a process’s working set — the pages actively used in a time window — doesn’t fit in available frames. The process faults repeatedly; evicted pages are immediately needed again; CPU utilization collapses. The fix: reduce multiprogramming. Fewer active processes means each gets more frames, allowing working sets to fit in memory.

Secondary Storage and Disk Scheduling

Virtual memory requires efficient disk access, so understanding disk performance is essential.

A Hard Disk Drive (HDD) stores data on spinning magnetic platters. Access time has three components:

  • Seek time — moving the arm to the right track (3–12ms typical)
  • Rotational latency — waiting for the sector to spin under the head (average = half a full rotation)
  • Transfer time — reading/writing the data once positioned (fast)

For a 7200 RPM disk: average rotational latency = ½ × (60s / 7200) = 4.17ms. Seek time dominates performance; minimizing unnecessary arm movement is the goal of disk scheduling.

FCFS: service requests in arrival order. Simple, but head movement can be large and erratic.

SCAN (elevator algorithm): sweep from one end to the other, servicing requests along the way, then reverse. Like an elevator — doesn’t skip back for requests behind it.

C-SCAN: like SCAN, but on the return trip the head jumps immediately back to the start without servicing. More uniform wait times — requests near one end don’t get double service.

SSTF (Shortest Service Time First): always service the nearest request to the current head position. Minimizes seek per request; can starve distant requests.

Board Exercise: Disk Scheduling

Request queue: 98, 183, 37, 122, 14, 124, 65, 67. Head starts at cylinder 53, moving upward.

For each algorithm, trace the head movement and compute total distance traveled: 1. FCFS 2. SCAN 3. C-SCAN 4. SSTF

Which minimizes total movement? Which gives the most uniform wait times? Which would you use on a heavy-write database server?

(Note: SSDs skip all of this analysis — no moving parts means seek time and rotational latency are essentially zero. Algorithms designed for HDDs are irrelevant to SSDs.)
