09 · OS Security

Learning Objectives

By the end of this lecture, you should be able to:

  • Classify security violations using the CIA triad and the five violation categories
  • Distinguish masqueraders, misfeasors, and clandestine users and explain which mechanisms defend against each
  • Describe how each layer of the four-layer security model works and what it protects against
  • Explain the principle of least privilege and apply it to a system design scenario
  • Compare symmetric and asymmetric cryptography and explain why both are used in practice

Think Like an Attacker

Security courses usually focus on defenses. This one starts differently: before you can design a defense, you need to understand what you’re defending against.

What does an attacker want? One of a few things:

  • Access to data they’re not supposed to see (read your files, intercept your traffic, steal credentials)
  • Ability to modify data they shouldn’t touch (change a grade, alter a transaction, inject malicious code)
  • Control of a system they don’t own (run code, host malware, mine cryptocurrency on your hardware)
  • Ability to prevent legitimate use (crash the service, hold files ransom)

Every security mechanism in the OS exists to make one of these goals harder. The uncomfortable truth is that no system is perfectly secure. The goal is to make attacks more expensive than they’re worth, detect breaches when they happen, and limit damage when they succeed anyway.

Opening Discussion

Before diving in: what security violations have you personally experienced or heard about recently? For each one, try to classify it: was it a confidentiality breach, an integrity breach, a denial of service? Who was the attacker — an outsider, an insider, automated malware? (This grounds the abstract framework in things students have actually seen.)

Security Violation Categories

Security violations map to what the attacker achieves:

  • Breach of confidentiality — unauthorized access to sensitive data
  • Breach of integrity — unauthorized modification of data
  • Breach of availability — unauthorized destruction of data or prevention of access
  • Theft of service — unauthorized use of system resources
  • Denial of service (DoS) — preventing legitimate use by flooding or crashing the system

The CIA triad (Confidentiality, Integrity, Availability) is the standard framework for thinking about what a security policy must protect. A good system design asks: for each piece of data or resource, who should be able to read it? Who should be able to modify it? How reliably must it be accessible?

Who’s Attacking?

Two broad sources of threats: humans (intruders) and automated programs (malware). Real attacks often combine both.

Masqueraders are outsiders who steal credentials and impersonate legitimate users. A hacker using a stolen password is a masquerader. Defense: strong authentication — make impersonation hard.

Misfeasors are legitimate insiders who exceed their authorized access — an employee reading HR files they have no business seeing, or an admin abusing privileges for personal gain. Their activity looks legitimate on the surface, making detection hard. Defense: granular access control and auditing.

Clandestine users gain privileged (root/admin) control and use it to disable logging and evade auditing. They attack the accountability layer — the goal is to act without evidence. Defense: tamper-evident logging, privileged operation monitoring.

Each type requires different defenses. The mistake is assuming all attackers look the same.

Class Activity: Classify the Attack

For each scenario, identify the intruder type and the appropriate countermeasure:

  1. A former employee still has VPN credentials three months after leaving the company
  2. A system administrator copies the customer database to a personal laptop
  3. An attacker gains root access and deletes all system logs before exfiltrating data
  4. An employee changes their own salary record in the HR system

Malware: Structure and Types

Malicious software (malware) falls into two structural categories:

Parasitic malware cannot exist independently — it attaches to legitimate programs and runs when they do. Viruses copy themselves into executables. Logic bombs are dormant code planted in legitimate programs, activating when a condition is met (a specific date, the absence of a particular account, a key input). Backdoors are hidden authentication bypasses — a hardcoded password or extra admin account — that persist after the initial compromise.

Independent malware runs as a standalone process. Worms spread across networks autonomously, exploiting vulnerabilities to replicate from machine to machine without any human action (no need to click an attachment). Bots are compromised machines participating in a botnet — a network of thousands of infected computers used collectively for spam, DDoS attacks, and further attacks.

Notable types:

  • Trojan horse — looks legitimate, secretly performs malicious actions. Up to 80% of spam has historically been delivered through spyware-infected machines whose owners had no idea.
  • Ransomware — encrypts your files, demands payment for the key. Key insight: paying doesn’t guarantee recovery. The only reliable defense is offline backups.
  • Spyware — harvests personal data (browsing habits, passwords, financial info), often bundled with “free” software.

All of these try to exploit or escalate privileges. A compromised web server account might pivot to root via a kernel vulnerability; a phishing email might capture credentials for a low-privilege account that has access to everything.

The Principle of Least Privilege

Every user, process, and component should have the minimum access necessary to do its job — no more. Jerome Saltzer articulated this in 1974 for the Multics OS:

“The purpose of this principle is to reduce the number of potential interactions among privileged programs to the minimum necessary to operate correctly, so that one may develop confidence that unintentional, unwanted, or improper uses of privilege do not occur.”

In practice: your web browser shouldn’t have access to your SSH keys. Your text editor shouldn’t make network connections. A compromised application should be limited in what it can destroy. When a breach occurs — and eventually it will — least privilege limits the blast radius.

Board Exercise: Apply Least Privilege

A web application needs to: serve static HTML files, write to a log file, read from a database, and send email notifications.

Design the minimum permission set for the web server process. What should it not be able to do, even though the server runs as a software process on the machine? For each permission you’d deny, explain what attack it prevents.

Four Layers of Defense

Security is layered — no single mechanism is sufficient, and defeating one layer should still leave others:

Physical security is the foundation. Physical access to a machine bypasses almost all software security. Countermeasures: locked server rooms, security cameras, full-disk encryption (a stolen drive contains only ciphertext), hardware security modules. Physical security is often the weakest link in small organizations.

Network security controls what enters and leaves. Attacks at this layer include packet sniffing (intercepting cleartext traffic), spoofing (forging source addresses), and on-path attacks (impersonating both parties in a communication). Countermeasures: encryption (TLS/HTTPS makes sniffed traffic useless), authentication (cryptographic proof of identity), and filtering (firewalls with strict ingress/egress rules).

Operating system security is where this course has spent most of its time. Attacks target insecure defaults, unpatched vulnerabilities, and misconfigured permissions. Countermeasures include regular patching, hardening (disabling unused services, strict permissions, removing unnecessary SUID binaries), and OS-level sandboxing via namespaces, seccomp filters, and containers.

Application security addresses bugs in software itself: logic errors, improper input validation, and memory safety violations. The buffer overflow attacks in the next lecture are application-layer attacks. Countermeasures include sandboxing applications (limiting which system calls they can make), software signing, and — critically — writing memory-safe code.

Key Pattern: Defense in Depth

An attacker who compromises your web server process should still face network controls preventing lateral movement. An attacker who gets on your network should still face host-based defenses. An attacker who compromises a low-privilege account should face access controls that prevent escalation. No single layer is impenetrable; the goal is that bypassing all of them requires disproportionate effort.

Authentication and Access Control

Authentication answers: who are you? Access control answers: what are you allowed to do? Both are necessary; neither alone is sufficient.

Authentication factors:

Factor Type Example
Something you know Secret Password, PIN
Something you have Token TOTP authenticator, smart card
Something you are Biometric Fingerprint, facial recognition
Something you do Behavioral Typing rhythm, mouse dynamics
Somewhere you are Location IP geolocation, GPS

Multi-factor authentication (MFA) combines two or more categories. A stolen password plus no physical token cannot authenticate. MFA is the single most effective defense against credential attacks — which represent the majority of real-world breaches.

An access control system mediates between authenticated users and system resources. It consults an authorization database and either permits or denies each request. An auditing component logs accesses for review and forensics. Access control policies range from discretionary (Unix file permissions — resource owners control access) to mandatory (OS enforces a central policy, no user override) to role-based (users are assigned roles; roles have permissions — used in enterprise systems).

Intrusion Detection

Prevention is imperfect; detection is essential. An IDS monitors system events and alerts on signs of unauthorized access.

An IDS has three components: sensors collect raw data (network traffic, system call traces, log files); analyzers examine sensor data to determine if an intrusion has occurred; a user interface presents findings and enables response.

Host-based IDS (HIDS) monitors a single machine — file access, system calls, process behavior. Detects attacks invisible to network monitoring. Limited to one host.

Network-based IDS (NIDS) monitors traffic for an entire network segment. Detects scanning, exploit attempts, and exfiltration across many machines simultaneously. Cannot see encrypted traffic or purely local attacks.

Cryptography as a Security Tool

Cryptography secures data in transit and at rest by making it unreadable without the right key.

Symmetric cryptography uses the same key for encryption and decryption. Fast; well-suited for bulk data. Challenge: distributing the shared secret securely — you need a secure channel to establish the secret key, which is the very problem you’re trying to solve.

Asymmetric (public-key) cryptography uses a key pair: a public key shared openly and a private key kept secret. Anything encrypted with the public key can only be decrypted with the private key. This solves key distribution — publish your public key, and anyone can send you an encrypted message only you can read.

Asymmetric cryptography is computationally expensive; in practice, it’s used only to securely exchange a symmetric session key (as in TLS), which then encrypts actual data traffic.

Discussion Prompt

You’re browsing your bank’s website over HTTPS. An attacker is monitoring your network traffic (on-path).

Walk through what they can and cannot do: - Can they read the contents of your requests? Why or why not? - Can they modify your requests before they reach the bank? - Can they see which server you’re connecting to? - What would need to fail for them to be able to read your traffic?

(This is a good way to ground TLS in a concrete threat model rather than abstract cryptographic promises.)
